# 龙智杯第四届智能空战大赛 — 项目说明

> 本仓库只包含**我方自己的工作记录**：开发时间线、训练与评测方法论、分析脚本与结论报告。
> **不包含**主办方发布的任何软件、平台、文档或示例策略，也不包含任何第三方代码。
> 详见 [`NOTICE.md`](NOTICE.md)。

---

## 1. 项目概况

- **赛事**：第四届"龙智杯"智能空战大赛（航空工业成都飞机设计研究所主办）。
- **任务**：为一支 2 机编队编写 Python 策略，在给定作战场景中与对手对抗。
- **交付形态**：高倍速训练版平台按槽位加载策略——`ACAS_01`~`ACAS_04` 各放
  `AIStrategy0X.py` + 支撑模块 + 在本机解释器内可运行的推理代码；一个 `SimuConfig.txt`
  可配置最多 N 个场景，平台一次运行跑完全部场景并写出 `Result/SimuResultReport.txt`
  与 `AcmiRecord/*.acmi`。
- **我方角色**：策略开发、训练、评测与调优；本仓库记录这一过程的**方法与结论**。

## 2. 技术架构

策略采用**分层结构**，这个分层是被平台的运行环境逼出来的，不是设计偏好：

```
┌──────────────────────────────────────────────┐
│ 规则状态机（确定性，拥有最终控制权）              │
│  · 导弹告警 / 交战规避 / 制导维持                │
│  · 边界恢复 / 返航                              │
│  · 火控校验（shootFlag、Rmax/Rtr、离轴角、能量） │
│  · 输出构造（指令必须指向本机，不能默认 1 号机）  │
├──────────────────────────────────────────────┤
│ ACE 偏好层（学习得到，只提供战术倾向）            │
│  · 局部观测 19 维 → 共享 actor → 10 个动作       │
│  · 动作 = patrol/approach/attack/evade/guide/   │
│         support/escort/breakthrough/            │
│         defense_line/search                     │
│  · 集中式 critic 38 维（仅训练期使用）           │
└──────────────────────────────────────────────┘
```

**为什么这样分层**：平台把策略跑在**嵌入式 Python 3.8 解释器**里，环境里没有 NumPy、
也没有 Torch。因此推理侧必须**只用标准库**；同时一旦 checkpoint 缺失或损坏，必须能
**退化回规则状态机**而不是返回非法输出。所以学习层只做"战术偏好"，不掌握发射与安全问题
的否决权。

**checkpoint 形态**：线性 actor（`ace-mappo-linear-v1`，10×obs 权重 + 10 偏置），
以 JSON 随策略一起部署，便于逐字节校验与版本对比。

**观测编码**：v2（19 维）为当前线上版本；v3（28 维，战场归一化位置 + 目标速度/方位/俯仰、
本机俯仰/过载/挂载、逐帧差分）已训练并测量，但在最难快照上回退（40 场里 33 → 27），
因此保持 opt-in（`ACE_OBS_LAYOUT=v3`），不随包发布。

## 4. 训练过程

### 4.1 最小可运行训练单元（MVP）

刻意**不**把仿真器包装成 Gym 环境，而是分成两半：

- **mock 环**（`train_mvp.py`）：验证算法契约——rollout、GAE、PPO 截断更新、
  ACE 变异体评估。零第三方依赖。
- **真实边界**（`sim_platform.py`）：只负责与平台的真实接口——调用仿真平台、
  解析 `Result/SimuResultReport.txt`、把比分作为奖励回传。

算法组件（`core.py`）：19 维局部编码器、10 动作共享 actor、38 维集中式 critic、
checkpoint 格式、精英池、软更新、对手课程。

### 4.2 自对抗与课程

- 精英池保存历史快照，对局在"当前策略 vs 历史快照/固定基线"之间轮换，避免自对抗退化。
- 课程：先对固定基线，再逐步混入更强的历史快照。
- 观测编码升级（v2 → v3）经过独立"最难受场景"筛查后才允许上线；v3 未通过，故回退。

### 4.3 部署边界

推理期确定性、纯标准库；学习层只产出战术倾向，**不掌握**发射许可与否决权。
坏 checkpoint 会退化到规则状态机，而不是产出非法平台字典。

## 5. 评测方法论（本项目最有价值的部分）

平台是高倍速、无 UI 的命令行程序，且**单次运行不可复现**。因此我们把评测做成了一套
可统计的方法，而不是"跑一批看比分"：

1. **固定场景集**：标准 20 个场景 × 5 次重复 = 100 场，编号 1–100，同一份
   `SimuConfig.txt` / `AreaConfig.txt`，跨批次可比。
2. **双方向镜像部署**：同一策略分别装到红方与蓝方，各 100 场，抵消先手/出生位置的结构性优势。
3. **严格同帧命中判定**：一枚导弹算命中，当且仅当它与**异色**飞机在**同一个 0.1 s 帧块内**
   被删除。（早期用"±1.5 s 且 ≤5 km"的宽松规则，会多造约 14 对假命中，已废弃。）
4. **ACMI × 平台调试日志联合**：ACMI 格式里**没有锁定目标字段**，只有发射方（`ShortName`
   括号内机号）、发射时刻与轨迹。我们从平台的调试日志里按（射手, 发射时刻）对齐取出
   `mslLockedTgtID` 与火控包线字段（`shootFlag`/`Rmax`/`Rtr`/`aspect`/`slantRange`），
   覆盖率 99%+。这一步是"同目标第 N 发"分析的前提。
5. **量化噪声底线**：同构建重复多批，测得命中率批间 SD 仅 0.47pp、发射量 CV 2.4%，
   而比分批间 SD 达 8–9 场。据此规定：**比分不做单批比较，效率类指标可做单批比较。**
6. **A/B 设计**：单开关改动 → 变体文件做**字节级 diff 证明**（只差目标常数）→
   双方向 × 多轮**交错**执行（抵消时间漂移）→ 逐场景配对检验（配对 t + Wilcoxon +
   场景聚类 bootstrap 95% CI）。
7. **轮换顺序**：如 3 轮交错采用"轮 1 A→B、轮 2 B→A、轮 3 A→B"，让批次顺序不偏向任一变体。

## 6. 关键结论汇总

### 6.1 系统性发现

- **平台不可复现**（09-12）：同一构建、同一场景集连跑两次，逐场胜负与 ACMI 哈希全部不同；
  5 场里有 2 场胜负翻转。**任何单批比分结论都必须带噪声条。**
- **补射灌水**（09-14，最大单项发现）：同一架飞机重复打同一目标——第 1 发命中率 43.5%、
  第 2 发 28.4%、第 3 发 2.9%、第 4 发 0.8%；60.8% 的发射属于这种自我重复。
  战术上的根因是：饱和计数器只统计**在飞**导弹，一发打空、计数归零后同一目标立刻"解禁"。
- **红/蓝严重不对称**：同一策略打红方 ~61%、打蓝方 ~99%。决定胜负的是"站哪一侧"，
  远大于任何单个开关的效应。
- **预警机失分是残局后果**（09-17，1200 场取证）：我方预警机被打 87 次、对手 8 次，
  且 87/87 全部导致失败；被击落时刻中位数 421 s（整局约 430–460 s），当时本方只剩 1 架
  战斗机、中位距离 148 km。**不是"护航被拉开"，是"护航已经打没了"**；
  且预警机槽位没有 Python 策略，不受我方代码控制。

### 6.2 开关级 A/B 一览

| 改动 | 结论 | 证据强度 |
|---|---|---|
| `guide_msl_cnt` 顺序缺陷修复 | 异常次数 6146 → 0；对胜率无可测影响 | 强（异常计数确定） |
| 蓝方防御线几何（09-15） | 无可测影响 | 中（单批 + 对照组同幅波动） |
| 补射上限 = 2（每机每目标） | 发射 −16%、命中 **+12%**、命中率 +8.7pp、比分 +12 胜 | 强（效率）/ 中（比分）；**最终未采纳** |
| 双闸门 `ACE_SUPPORT/BREAKTHROUGH_AUTHORITY` | 无可测影响，95% CI [−3.7%, +4.2%] | **强**（每变体 600 场，逐场景配对） |

> 关于"补射上限"：效果明确且机制被验证（第 3/4 发精确归零），但项目最终**未采纳**该改动。
> 本仓库如实记录实验与数据，供后续判断。

## 7. 复现指南

```text
scripts/
  analyze_manual100.py      # ACMI 层指标：发射/命中/越界/突防（严格同帧规则）
  report_manual100.py       # 单批 markdown 报告
  compare_runs.py           # 两批对照（含逐场翻转表）
  report_vs_baseline.py     # 双方向 plus-vs-基线对照报告
  ab_stats.py               # 多批重复 A/B 的逐场景配对统计
  gates_stats.py            # 同上，用于双闸门 3x200 批次
  waste_analysis*.py        # 逐弹发射效率（含严格命中口径）
  waste_join_analysis.py    # ACMI x 调试日志：同目标第 N 发
  waste_crosstab.py         # 剥离"距离 vs 第几发"的混杂
  ewa_analysis*.py          # 预警机失分取证
  make_gate_variants.py     # 生成单开关变体 + 字节级 diff 证明
  add_throttle.py           # 补射上限补丁（单开关）
  run_*.ps1                 # 批次驱动（部署→跑→归档→分析）
```

典型流程：

1. 把变体策略放进各槽位的 `Pythonstrategy/`（`AIStrategy0X.py`）。
2. 用 `run_*.ps1` 逐批驱动：清空 `Result/`、`AcmiRecord/`，跑平台，归档，调分析脚本。
3. 用 `ab_stats.py` / `gates_stats.py` 做逐场景配对检验，看 **95% CI 是否含 0**。

数据文件：`data/waste_by_scenario.csv`（20 个基础场景的发射/命中/命中率）。

## 8. 已知限制

- 平台**无随机种子控制**，只能靠重复批次与配对统计来压制噪声。
- 调试日志的包线字段是**每 25 帧（≈2.5 s）**采样，不是发射瞬间，火控判定为近似。
- 上述结论均基于**标准 20 场景集**与**单一对手基线**；换场景或换对手未必成立。
